## Architecture

### Three scheduled services (do not merge)

The system runs as three separate scheduled entrypoints that must remain independent:

- **`main.py`** — End-of-day pipeline (4:30 PM). Runs: regime check (XIU.TO vs 200-day SMA) → universe builder (`swing_tickers.py`) → screener → entry pipeline → send report. Skips signal generation in bear regime but still sends a report.
- **`virtual_buy.py`** — Virtual entry execution (9:45 AM). Reads pending intents and cash from the database, sizes positions using `RISK_PER_TRADE_PCT` from `config.py`, and writes new positions back to the database, persisting each intent's planned `stop_price` onto the position. Skips execution outside TSX trading hours via `is_market_open()` (a `--dry-run` is still allowed any time). Also enforces `MAX_POSITIONS_PER_SECTOR` (via `sector_lookup.get_sector()`), skipping a candidate whose GICS sector already holds the cap's worth of open positions — added 2026-08 after a live cluster of same-sector earnings-week stop-outs; 16-fold walk-forward showed no return cost but a significant max-drawdown reduction.
- **`position_monitor.py`** — Position monitoring / virtual exits (3:50 PM pre-close and post-close). Reads open positions from the database and applies exit rules, honouring the position's persisted `stop_price` as the initial stop when present. Off-hours pre-close runs fall back to daily bars and suppress sells via `is_market_open()`.

### Data flow

```
<CAN_TICKERS_URL>  (remote URL, one ticker per line)
  → canadian_stock_screener.py (StockScreener + DataManager)
  → out/screener_out/YYYYMMDD_HHMM.csv
  → auto_pipeline.py (pattern detectors + signal state machine)
  → out/alerts/, out/report.html
  → data/trading.db [signals, intents tables]
  → virtual_buy.py → data/trading.db [positions, transactions, account tables]
  → position_monitor.py → data/trading.db [trades, transactions tables]
```

### Key modules

- **`config.py`** — `CAN_TICKERS_URL` (the single ticker list URL), output paths, and trading parameters (`MAX_POSITIONS`, `RISK_PER_TRADE_PCT`, `GAP_FILTER_PCT`, `MAX_POSITIONS_PER_SECTOR`, `PositionMonitorMode`).
- **`sector_lookup.py`** — `get_sector(ticker)`: GICS sector lookup for the `MAX_POSITIONS_PER_SECTOR` cap in `virtual_buy.py`, via yfinance `.info['sector']`, cached to `cache/sector_cache.json` (sectors change rarely).
- **`db.py`** — DuckDB persistence layer. All live-mode state lives in `data/trading.db`. Call `init_db()` at the start of each service. Six tables: `account` (cash), `positions` (open, incl. the planned `stop_price`), `trades` (closed, append-only), `signals` (pipeline state machine), `intents` (buy queue), `transactions` (unified BUY+SELL ledger). Schema changes are straightforward — DuckDB supports full `ALTER TABLE`; `init_db()` self-migrates the `stop_price` column via `ADD COLUMN IF NOT EXISTS`.
- **`time_utils.py`** — Injectable backtest clock. `set_backtest_clock(dt)` pins time for simulation; `None` restores live wall-clock. All time-dependent code calls `market_now()` / `market_today()` from here. `is_market_open()` (weekday + 09:30–16:00 ET + TSX holiday set) guards the live services from transacting off-hours and is deterministic under the backtest clock.
- **`market_data.py`** — Two data providers behind a structural interface (`MarketDataProvider`): `LiveDataProvider` (wraps yfinance for live mode) and `HistoricalSliceProvider` (pre-loaded dict with strict `as_of` cutoff to prevent lookahead bias). This is also the project-wide isolation boundary for Yahoo Finance: no module outside this file imports `yfinance` directly — `sector_lookup.py`, `market_data_cache.py`, `conviction_watchlist/` (`quality_filter.py`/`entry_screener.py`/`trailing_stop_monitor.py`), and the standalone research scripts `research/elder_ray.py`/`research/elder_ray_backtest.py`/`dip_grid_backtest.py` all go through `LiveDataProvider`'s methods (`get()`, `get_info()`, `download_bars()`, `download_range()`) instead of calling yfinance themselves, "research" included — a gap fixed 2026-09-14 (the scripts previously each carried their own copy-pasted `yf.download()` fetch). Two exceptions are intentional, not gaps: `demand_signals/options_flow.py`'s `YahooOptionsProvider` and `research/triple_screen/yfinance_provider.py` each wrap yfinance behind their *own* documented ABC (`OptionsFlowProvider` / `DataProvider`) for a data shape `MarketDataProvider` doesn't cover (an options chain snapshot; a research package meant to stay decoupled from the rest of the repo) — still isolated, just via a different interface. Adding a new yfinance call site anywhere else should instead be a new method on `LiveDataProvider` (or a new provider-ABC implementation, for a genuinely different data shape).
- **`backtest_runner.py`** `BacktestConfig.gap_filter_pct` — `None` (default) = no gap filter, matching pre-2026-05 backtest behaviour and the live `GAP_FILTER_PCT` (set to `None` 2026-07 after a fixed-value head-to-head showed the filter reduced returns at every level; was `2.0`). Set to e.g. `2.0` to simulate a gap filter (skip buys where open > intent_entry × 1.02).
- **`backtest_runner.py`** `BacktestConfig.max_per_sector` / `.sector_map` — `None` (default) = no sector cap. Pass a cap (e.g. `2`) and a `{ticker: sector}` dict to simulate `MAX_POSITIONS_PER_SECTOR`; a candidate is skipped once its sector holds the cap's worth of open positions, mirroring `virtual_buy.py`'s live enforcement.
- **`portfolio.py`** — In-memory `PortfolioState` for backtesting only. No file I/O; the live-mode equivalent is `db.py`.
- **`backtest_runner.py`** — Day-by-day simulation. For each day: after-close screener + pipeline, then next-open buys at open price, then daily position monitor.
- **`canadian_stock_screener.py`** — Multi-factor momentum screener (Weinstein Stage II, RS vs XIU.TO, MACD, OBV, ADX, VAM, 52w proximity). Universe and weights controlled by `CONFIG` dict inside the file.
- **`auto_pipeline.py`** — Consumes screener CSV outputs, runs three pattern detectors (VCP, EMA pullback reclaim, base breakout), advances a signal state machine (`FORMING → AT_PIVOT → CONFIRMED → ACTIVE/FAILED`), and writes confirmed intents to the database.
- **`send_report.py`** — Gmail SMTP sender. Has two distinct responsibilities: `send_report()` sends the daily HTML pipeline report (called from `main.py` and `position_monitor.py`); `send_transaction_email()` / `build_transaction_html()` sends a trade notification email after every buy or sell (called from `virtual_buy.py` and `position_monitor.py`). `send_text_email(subject, body)` sends a plain-text email (used by the EDGAR collector). Credentials are read from `.env` (`GMAIL_SENDER`, `GMAIL_APP_PASSWORD`, `GMAIL_RECIPIENT`). Silently skips if not configured.
- **`edgar_service.py`** / **`edgar/`** — Separate 4th service (US SEC EDGAR), the fundamentals/ownership counterweight to the TSX momentum system. Daily after the US close it sweeps EDGAR's daily index, stores filings in its OWN SQLite DB (`data/edgar.db`, keyed on CIK+accession — NOT `trading.db`), and emails a plain-text digest of flagged hits (interim: watchlist insider purchases (Form 4 code 'P' — open-market or private, not distinguished in the data) + all SC 13D/13G, plus new Section 16 filers via Form 3) via `send_report.send_text_email()`. Quiet day = no email. Reuses shared config/email/logging/lock; stays independent of the TSX trio (US filers only). Config in the `EDGAR_*` block of `config.py`; dev sandbox + specs in `edgar/`. Every filing is a lagged disclosure — a research trigger, not a price predictor. `edgar_report.py` is a separate on-demand command that parses already-collected 13D bodies from `scan_hits` and emails a digest.
- **`demand_signals_service.py`** / **`demand_signals/`** — 5th service, added 2026-09: a "real buyer demand" tracker normalizing four US-market sources into one schema (`demand_signals.schema.DemandSignal`: ticker/us_ticker/date/source/signal_type/direction/strength/lag_days/detail, persisted in its OWN SQLite DB `data/demand_signals.db` via `demand_signals/store.py`) so they're screenable together per ticker. `source='edgar_insider'` (`edgar_adapter.py` reads-only from `edgar.db`'s `insider_buys` — never re-fetches, never writes back), `source='finra_darkpool'` (`darkpool.py`: FINRA's free Query API, but OAuth2 client-credentials, not an anonymous GET like SEC's — `FINRA_CLIENT_ID`/`FINRA_CLIENT_SECRET` read from `.env` by `darkpool.py` itself, same self-contained pattern as `send_report.py`'s `GMAIL_*`, since `config.py` doesn't load `.env`; flags a ticker whose weekly ATS-volume ratio has risen `DEMAND_DARKPOOL_RISING_WEEKS` (3) consecutive weeks — WEEKLY data with its own ~2-week publication lag, a confirmation signal only, never a live trigger), `source='finra_short_volume'` (`short_volume.py`: FINRA's daily consolidated (CNMS) Reg SHO short-sale-volume file at `cdn.finra.org` — a plain unauthenticated download, unlike `darkpool.py`'s OAuth2 Query API, published T+1; flags a ticker whose daily short-volume/total-volume ratio has fallen (`short_volume_covering`, bullish — short sellers stepping back) or risen (`short_volume_pressure`, bearish) `DEMAND_SHORTVOL_TREND_DAYS` (3) consecutive sessions; added because the ~2-week ATS lag was judged too stale to act on while Form 4's ~5-day lag was acceptable — this source's T+1 lag clears that bar), `source='options_flow'` (`options_flow.py`: a pluggable `OptionsFlowProvider` ABC, one free implementation `YahooOptionsProvider` via yfinance's option chain — a SNAPSHOT, not a trade tape, no sweep/block detection; a paid vendor plugs in as a second implementation without touching callers). `demand_signals/http_cache.py` generalizes `edgar/core.py`'s rate-limit+cache pattern but is a separate implementation with its own per-source `RateLimiter`/cache-dir instances (`edgar/core.py` itself untouched) — sharing one rate budget across SEC/FINRA/Yahoo would incorrectly couple unrelated hosts' limits. `demand_signals/ticker_map.py` is a hand-curated CAN→US symbol table for interlisted names (`config.py`'s EDGAR_FORMS/watchlist precedent, not automated inference); a Canadian-only name (no US line) gets no `finra_darkpool`/`finra_short_volume`/`options_flow` signal until a SEDI (Canadian insider) source exists — the module's own extension-point comment marks where another `source` value would go. Config in the `DEMAND_*` block of `config.py`; scheduled via `stockscanner-demand-signals.timer` (22:00, after edgar's 21:30 run, so its EDGAR-adapted signals see that day's `insider_buys`). No email digest yet, same "interim" staging EDGAR itself started with — `demand_signals.store.signals_for_ticker()` is the screener-facing read path; the dashboard's `/demand` route (`demand_dashboard_data.py`) is the human-facing one.
- **Support modules** — `report.py` (console dump of the live trading DB: cash, positions, trades, signals, intents), `report_html.py` (light-theme HTML email report — Gmail forcibly overrides dark backgrounds), `schema_keys.py` (shared column/field keys used across pipeline, buy, monitor, and report modules), `concurrent_utils.py` (fcntl file lock in `out/locks/` preventing overlapping service runs), `log_utils.py` (JSON run logging via `market_now()`).
- **`manual_sell.py`** — on-demand CLI to close one open position at the current market price (live 5-min intraday snapshot, falling back to the last daily close). Takes a single ticker argument; reuses `position_monitor.execute_virtual_sells()` so the position removal, cash credit, trade record, and transaction email match every other sell path. `--dry-run` previews without writing. Core logic lives in `sell_position(ticker, dry_run=False) -> dict` so both the CLI and the web dashboard call the same code.
- **`dashboard_app.py`** / **`dashboard_positions.py`** — Flask + Waitress web dashboard (LAN-only, no auth — deliberate for a home-network Jetson deployment). `dashboard_positions.build_live_positions()` is a read-only, TTL-cached mirror of `position_monitor.py`'s live per-position pipeline (never calls `execute_virtual_sells` itself — a "SELL" status shown here is informational only). Routes: `/` (Monitor, incl. the sell button), `/history` (closed trades + transaction ledger), `/momentum` (momentum sleeve, read-only), `/macro` (macro conviction sleeve, read-only, also surfaces the current macro regime label/composite/votes via `macro_dashboard_data.get_current_regime()`), `/demand` (`demand_dashboard_data.py`, read-only mirror of `demand_signals.db` — same isolation pattern as `momentum_dashboard_data.py`: its own sqlite connection, never `demand_signals/store.py`'s `connect()`, never a fetch/write from this process), `/triple-screen` (`triple_screen_tracker_dashboard_data.py`, read-only mirror of `triple_screen_tracker.db`, same isolation pattern), `/kangaroo` (`kangaroo_dashboard_data.py`, read-only mirror of `kangaroo.db`, same isolation pattern — also surfaces still-pending/untriggered breakout setups), `/scanner` (`scanner_dashboard_data.py`, read-only mirror of `scanner_board.db`, same isolation pattern — see the Scanner Board entry below), `/conviction` (`conviction_dashboard_data.py` — read/write, the only tab besides Monitor's sell button that mutates state; POSTs rebuild the quality list, refresh candidates, and edit real-account holdings), `POST /api/positions/<ticker>/sell` (calls `manual_sell.sell_position()`), `/healthz`. Templates in `templates/`, assets in `static/`. Deployed via `system/stockscanner-dashboard.service` (the first always-on `Type=simple` unit in this repo — the others are `Type=oneshot` + `.timer`).
- **Momentum sleeve** (`momentum_pipeline.py`, `momentum_buy.py`, `momentum_monitor.py`, `momentum_dashboard_data.py`) — a second, fully isolated paper account (`data/momentum.db`, `config.py` `MOMENTUM_*`), added 2026-08 after diagnosing that the core sleeve's universe builder (hard `atr_pct_14 > 5%` rejection in `swing_tickers.py`) and its three pattern detectors (all require a basing/consolidation structure) structurally cannot buy a vertical sector move (e.g. the 2026-08 gold/silver miner rally). `momentum_pipeline.py` builds its own universe each run via `swing_tickers.run_universe_builder()` with `MOMENTUM_MAX_ATR_PCT` (0.20) against the raw pre-filter ticker source (`MOMENTUM_RAW_TICKERS_URL`, since the published `CAN_TICKERS_URL` is already ATR-filtered upstream), runs with `regime_filter=False` (a broad-index gate would block exactly the sector-specific rallies this sleeve targets), and `enable_momentum_breakout=False` (see below). `momentum_buy.py` is a structural fork of `virtual_buy.py` (own `MOMENTUM_MAX_POSITIONS`/`MOMENTUM_RISK_PER_TRADE_PCT`, own DB) rather than a parameterisation, matching the "services stay independent" precedent already set by EDGAR. `momentum_monitor.py` reuses `position_monitor.compute_signals()`/`execute_virtual_sells()` by import with a wide chandelier `ExitParams` (`MOMENTUM_CHAND_TRAIL_ATR_K=4.0` vs the core's 2.5 — the one exit parameter actually validated by the 2026-08 walk-forward; initial stop distance is untouched, still `PipelineConfig.atr_stop_mult`'s default). `momentum_dashboard_data.py` deliberately never imports `db.py` — it opens its own read-only DuckDB connection to `MOMENTUM_DB_PATH` so the dashboard's single long-running process can serve both sleeves concurrently without racing on `db.py`'s module-global `DB_PATH`; no manual-sell route exists for this sleeve yet for the same reason. `auto_pipeline.py`'s `_detect_momentum_breakout` (a 4th detector, no base-range requirement) exists behind `PipelineConfig.enable_momentum_breakout` but ships **off**: a 16-fold walk-forward (2021-06→2025-06) found it added trades with no statistically significant return edge (p=0.836) and a directionally worse drawdown. The sleeve itself (relaxed universe + wide chandelier trail, 3 existing detectors) was walk-forward validated on the same fold structure as the core sleeve's own 2026-08 risk% test: ~2x the core sleeve's average per-fold return, ~1.5x the average drawdown — a real trade-off, which is why it runs as a separate, walled-off account instead of a core-sleeve config change.
- **Macro conviction sleeve** (`macro_regime.py`, `macro_buy.py`, `macro_monitor.py`, `macro_dashboard_data.py`) — a 6th, fully isolated paper account (`data/macro.db`, `$10,000` starting capital, `config.py` `MACRO_*`), added 2026-09, loosely inspired by Stanley Druckenmiller's approach: read the macro/liquidity backdrop first, then take concentrated conviction bets on top of already-vetted candidates, capital-preservation-first on exit. Long-only (no shorting infrastructure exists in this repo) — a hostile regime reading means "go to cash," never "go short." `macro_regime.py` fetches 3 free FRED (St. Louis Fed) series and votes each +1/0/-1 over its own native-frequency consecutive-trend lookback window (`MACRO_CURVE_TREND_DAYS`/`MACRO_CREDIT_TREND_DAYS`/`MACRO_LIQUIDITY_TREND_WEEKS`, all =5/5/3, unvalidated starting points — no backtest exists for this sleeve yet): `T10Y2Y` (10y-2y yield curve, daily, bullish if rising/steepening), `BAMLH0A0HYM2` (ICE BofA US High Yield OAS, daily, bullish if falling/tightening), `WALCL` (Fed total assets, weekly, bullish if rising — the direct "central bank liquidity" signal Druckenmiller himself has cited). `composite = sum(votes)` in `[-3,+3]`, thresholded at zero into `risk_on`/`neutral`/`risk_off` — no tunable float threshold needed. `FRED_API_KEY` is read from `.env` by `macro_regime.py` itself (same self-contained pattern as `demand_signals/darkpool.py`'s FINRA creds); if unset, every series votes 0 and the reading is `"neutral"` — a fail-safe, not an error, so the sleeve just stays in cash until the key is configured. This sleeve has **no own screener/pipeline** — unlike the momentum sleeve's `momentum_pipeline.py`, there is no `macro_pipeline.py`, so `macro_buy.py`'s `__main__` itself seeds `MACRO_INITIAL_CAPITAL` on first run (`get_cash() <= 0` check, same pattern `momentum_pipeline.py` uses) since it's the sleeve's earliest daily touchpoint. `macro_buy.py` reads the **core** sleeve's own already-confirmed `intents` (`data/trading.db`) read-only via a raw `duckdb.connect(..., read_only=True)` query (captures `db.DB_PATH` at import time as `CORE_DB_PATH`, since `db.init_db(path=...)` mutates that same module-global — this module never calls `db.init_db()` against the core DB, and **never** calls `mark_intent_executed()`/`mark_intent_skipped()` on a core intent row, which would make `virtual_buy.py` silently skip/lose real intents). It buys nothing at all unless the regime reads `risk_on`; when it does, candidates are ranked by `rr` (reward:risk) descending — the only per-intent quality signal that reaches `intents` today, since `canadian_stock_screener.py`'s `composite_score` is dropped by `auto_pipeline._read_screener_file()` before it gets there (a named, not-yet-built future extension). A Kangaroo Tail is a bullish "false-breakdown + reject" candle: a small body, a dominant lower wick, closing back into the upper half of its own range. Phase 2's 16-fold walk-forward event study found NO edge for buying at the tail's own close under any threshold combination tested — but a separate, risk-defined R-multiple breakout backtest (stop at the tail's low, target a multiple of that risk, entry only once price actually trades through the tail's own high) found a real, if modest, edge for that specific entry mechanic (win 56.6%, avg_R +0.246, profit factor 1.72, 16-fold-paired t-test p=0.033 at rr=1.5, n=143 trades, using the shipped `TailConfig` defaults — see `research/kangaroo_tail/types.py`'s docstring). ADD COLUMN IF NOT EXISTS`, same precedent as `stop_price`) — `NULL`/unused by every other sleeve. `kangaroo_dashboard_data.py` mirrors `momentum_dashboard_data.py`'s own-read-only-DuckDB-connection pattern exactly and additionally surfaces still-pending (untriggered) breakout setups from the `intents` table. - **Press-release tracker** (`press_release_service.py`, `press_release_tracker/`) — a 10th, fully isolated service, added 2026-09: unlike every sleeve above, **no capital, no positions at all** — same "pure collector" shape as EDGAR/demand-signals, not a paper-trading sleeve. Grew directly out of the Volume spike scanner's own research below: the same-day intraday edge is real, but capturing it needs the catalyst detected fast, and a press release is very often that catalyst (see the OMI.V case study in MEMORY). Polls every feed in `config.PRESS_RELEASE_FEEDS` (starts with one — GlobeNewswire's "News from Canada" RSS feed; a plain list so a second/third source is just another URL appended, no code change), fetched mechanically by `press_release_tracker/feeds.py` (stdlib `xml.etree.ElementTree`, no `feedparser` dependency needed for one well-formed RSS 2.0 feed) with no interpretation at that layer — deliberately, since the user wants the LLM itself to be "the parser" rather than a deterministic ticker/category extractor. `press_release_tracker/store.py` (own SQLite DB, `data/press_releases.db`, same self-migrating-schema-string-no-ORM convention as `edgar/store.py`/`triple_screen_tracker/store.py`) dedupes every item by its RSS `guid` (falling back to `link` when a feed omits one) in `seen_items` — this service polls every 5 minutes (see its timer), so the same item is refetched every run until it ages out of the feed's own window. `press_release_tracker/llm_parser.py` sends each new item's title/description/categories to the OpenAI API (`OPENAI_API_KEY` read from `.env` by this module itself, same self-contained pattern as `demand_signals/darkpool.py`'s FINRA creds / `macro_regime.py`'s FRED key) and gets back `{ticker, company, category, materiality, summary}` as JSON; unconfigured or a failed call returns `None` and the item is still emailed with its raw RSS title/link, just unclassified — the same "degrade gracefully" convention as every other optional credential in this repo. Model is `config.PRESS_RELEASE_LLM_MODEL` (`"gpt-5-nano"`, OpenAI's cheapest/smallest text tier — this short-text classify+summarize task doesn't need a frontier model; a one-line config change if a cheaper/better tier appears later). Unlike `triple_screen_tracker_service.py`'s day-keyed `email_log` (one row per daily run), "already emailed" here is tracked per item (`seen_items.emailed`), since this runs many times a day — a quiet cycle (nothing to send in either lane) sends nothing, the same convention as `edgar_service.py`/`demand_signals_service.py`. Runs every 5 minutes, all day, every day, with no market-hours gate at all (unlike every trading service) — press releases can break pre-market or after hours, which is the entire point of tracking them. No dashboard tab yet.

  Delivery is split into two lanes on the LLM's own `materiality` read (added 2026-09 after the first live test showed a busy newswire morning would otherwise trigger an email almost every 5-minute poll): a `materiality='high'` item emails immediately, its own run, never batched — the whole point of this sleeve is catching a market-moving catalyst fast. Everything else (`medium`/`low`/unclassified, e.g. `OPENAI_API_KEY` unset) accumulates and flushes as one digest at most every `config.PRESS_RELEASE_BATCH_INTERVAL_MINUTES` (60) — `press_release_tracker/store.py`'s single-row `batch_state` table tracks when that last actually sent (`None` reads as "due immediately", so the very first batch doesn't wait out a full hour on a fresh DB). Both lanes share one subject prefix, `press_release_tracker/digest.py`'s `SUBJECT_PREFIX = "Stock News Results"` — the user's own explicit ask, so every email this sleeve ever sends can be filtered on that one string in an email client regardless of which lane sent it.
  Backtest research (2026-09, three scripts, root-level, same one-off-research-script convention as `dip_grid_backtest.py`/`walk_forward_ab.py`): is this signal actually profitable, and does its own live-tool "your first 6 picks all closed up today" observation hold up? **`volume_spike_intraday_backtest.py` is RETRACTED** — its checkpoint/hold sweep (curated-46, full-~900, expanded-106, open-hour universes) summed yfinance HOURLY bars for "volume so far," which turned out to materially undercount real TSX volume (confirmed empirically: one name's hourly-bar sum for a single day came back 6.5x-12x below that same day's real daily-bar volume, most names 1.1x-2.4x, erratic even for one ticker across days — likely dark-pool/off-exchange prints missing from the intraday feed but present in the end-of-day consolidated tape). Every checkpoint that script tested, "close" included, was built on this broken number, so none of its conclusions can be trusted. Two corrected scripts replace it, both using ONLY the accurate daily-bar feed for volume (immune to the bug): **`volume_spike_daily_backtest.py`** tests buying at a CONFIRMED spike's CLOSE and holding 1-10 trading days forward — NEGATIVE at every horizon, extremely high confidence (900 tickers, 4yr, n=121,764 events, t -7 to -11, p~0, negative in every one of 16 folds); a follow-up survival-style check found spike days give back FASTER than an ordinary day, not slower (median 1 trading day to first close below the spike-day close, vs. 2 for an ordinary day; only 15.3% never dip below that close within 20 trading days, vs. 17.9% for an ordinary day) — whatever drove the spike is priced in during that one session, not over the following days/weeks. **`volume_spike_same_day_backtest.py`** tests the question that actually matters — buying INTRADAY on a day that turns out to be a confirmed spike (daily-bar detection; hourly bars used ONLY for the midday price, which was never the broken part, rescaled onto the daily-adjusted basis the same way `volume_spike_intraday_backtest.py`'s `_checkpoint_reads()` already did) and exiting at THAT SAME day's close — POSITIVE, 16/16 folds, t=18.75, p~0 (106-name liquid-TSX universe, ~2yr hourly-bar ceiling, 15,302 events: 63.1% win rate / +0.275%/trade vs. 46.3% / -0.045% baseline). **Net conclusion: the edge is real but strictly intraday** — ride a confirmed spike to that day's close, never buy-and-hold past it. Turning this into a live strategy would need an intraday trigger-watching loop (`kangaroo_buy.py`'s own precedent, not `virtual_buy.py`'s once-daily pattern) and wasn't built — this is recorded as a validated research finding, not (yet) a sleeve.

### Deployment (systemd)

`system/` holds `.service`/`.timer` units for the four core services (main, buy, monitor, edgar) plus the three momentum-sleeve services (momentum-pipeline, momentum-buy, momentum-monitor — same schedule as their core counterparts) plus demand-signals (22:00, after edgar's 21:30) plus the two macro-sleeve services (macro-buy, macro-monitor — same 09:45/15:50 schedule as their core/momentum counterparts; no macro-pipeline unit, since this sleeve has no own screener) plus triple-screen-tracker (17:00, after main's 16:30) plus the three kangaroo-sleeve services (kangaroo-pipeline at 16:30, same slot as momentum-pipeline; kangaroo-buy at **15:45**, NOT virtual_buy.py's 09:45 — it's an intraday breakout-trigger check, not a next-day-open fill, so it needs most of the day's range to have formed first; kangaroo-monitor at 15:50, right after kangaroo-buy so a freshly triggered position is also checked for stop/target the same cycle) plus scanner-pipeline (17:15, after triple-screen-tracker's 17:00 — no capital/positions, so unlike every sleeve above it has no buy/monitor units, only the one pipeline) plus press-release (every 5 minutes, all day, every day — no market-hours gate, unlike every trading service, since press releases can break pre-market or after hours; also no capital/positions, so only the one unit). All timers deliberately use `Persistent=false`: a slot missed while the host was down is skipped, not run late on stale prices. Do not change this to `true` — off-hours catch-up runs previously caused fills at stale quotes; `is_market_open()` is the second layer of the same defence. `conviction_watchlist` has no systemd unit at all — it's driven entirely from the `/conviction` dashboard tab, not a scheduled service; the volume spike scanner (`volume_spike_scanner.py`) likewise has no systemd unit — it's driven entirely from the `/volume-spikes` dashboard tab, re-scanning live on every load. Install/status commands are in `README.md` ("Systemd deployment") and `system/info`.

- `data/press_releases.db` — own SQLite store for the press-release tracker (`press_release_tracker/store.py`) — `seen_items` (RSS-guid-keyed dedupe + emailed flag) + `parsed_releases` (LLM output); no capital/positions schema at all, same shape as `scanner_board.db` above.
- `data/conviction_holdings.json` / `data/conviction_settings.json` / `data/conviction_entry_candidates.json` — plain JSON state for `conviction_watchlist/` (not a DB at all; machine-local, gitignored).
- `out/` — generated outputs (screener CSVs, alerts, HTML report, logs, locks); momentum-sleeve equivalents are prefixed `momentum_` (see `config.py` `MOMENTUM_*_PATH`).

### Querying the database

```python
import duckdb
conn = duckdb.connect("data/trading.db")

conn.execute("SELECT * FROM transactions ORDER BY trade_date").df()   # full ledger
conn.execute("SELECT * FROM positions").df()                          # open positions
conn.execute("SELECT * FROM trades ORDER BY sell_date").df()          # closed trades
conn.execute("SELECT * FROM intents WHERE intent_status = 'PENDING'").df()
conn.close()
```
